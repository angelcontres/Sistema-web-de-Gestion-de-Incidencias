# 1. Estrategia General de Pruebas

## 1.1 Alcance

Las pruebas propuestas para la siguiente entrega contemplan:

- Validación funcional, de integración y de interfaz en los módulos más críticos del sistema:
  - **Gestión de Incidencias:** Operaciones completas de CRUD.
  - **Registros de Estados y Trazabilidad:** Registros históricos de campos de auditoría como autor, fecha de modificación y modificaciones realizadas.
  - **Roles y Asignación:** Verificación de la asignación de roles y responsabilidades en incidencias específicas.
  - **Notificaciones:** Validación del sistema de comentarios y alertas con sus respectivos estados de casos atendidos y no atendidos.
  - **Validación de Entradas:** Manejo de datos de entrada mediante validaciones en el frontend y correcto uso de las respuestas por parte del backend.

## 1.2 Fuera del Alcance

En las siguientes pruebas no se contemplan:

- Pruebas de penetración.
- Pruebas de disponibilidad.
- Recuperación ante desastres.
- Auditorías sobre infraestructura distinta al entorno Docker definido para el proyecto.

## 1.3 Perfiles

Aunque cada integrante mantiene un área principal de responsabilidad (Frontend, Backend y Base de Datos/Infraestructura), el diseño y revisión de los casos de prueba será realizado de forma colaborativa mediante revisiones cruzadas entre los integrantes para garantizar objetividad.

- **QA Frontend:** Evaluará la interfaz, validaciones visuales en Bootstrap y el consumo y tratamiento de las respuestas por parte de las API REST.
- **QA Backend:** Auditará la lógica de negocio en Laravel, respuestas de la API REST y seguridad de las rutas.
- **QA Data & Deploy:** Validará la persistencia en la base de datos (integridad referencial, normalización) y el correcto funcionamiento dentro del entorno Docker.

## 1.4 Fechas Tentativas y Entornos

- **Fase de Diseño (Hito 3):** Creación de casos documentados (Actual).
- **Fase de Ejecución (Hito 4):** Las pruebas se ejecutarán en un entorno local replicado mediante Docker, previo a la socialización final del proyecto.

## 1.5 Tipos de Evidencias a Capturar

Se planifica recopilar las siguientes evidencias durante la fase de ejecución (Entregable 4):

- Capturas de pantalla de la interfaz con los resultados de las validaciones en formularios.
- Respuestas de los servicios web (JSON) para confirmar el manejo de errores.
- Métricas básicas de pruebas de carga sobre las funcionalidades principales del sistema.

# 3. Clasificación de las Pruebas

Para garantizar una cobertura integral del Sistema Web de Gestión de Incidencias Georreferenciadas, se ha segmentado metodológicamente en tres categorías principales.

## 3.1 Pruebas Funcionales (15 Casos)

Evaluación del comportamiento de los flujos lógicos del negocio, operaciones CRUD y trazabilidad del sistema, con el objetivo de verificar que las entradas válidas produzcan las salidas esperadas en el modelo relacional.

Incluye funcionalidades relacionadas con:

- Flujo de Creación y Trazabilidad.
- Motor de Historial.
- Auditoría de Datos.
- Motor de Consultas y Métricas.

## 3.2 Pruebas de Validación de Entradas (5 Casos)

Auditoría sobre la robustez del sistema frente a datos anómalos, formatos incorrectos y el respeto de las restricciones físicas o lógicas del esquema.

Incluye:

- Límites Geográficos.
- Integridad del Borrado Lógico.
- Validación de Tipos de Datos.

## 3.3 Pruebas de Seguridad Preliminar (5 Casos)

Verificación de los mecanismos de autenticación, protección de rutas y el modelo de Control de Acceso Basado en Roles implementado.

Incluye:

- Control de Accesos por Rol.
- Protección de Opciones de Menú.
- Validación de Sesión/Tokens.

# 4. Técnicas de Diseño Aplicadas

Para garantizar cumplir con los estándares de la industria, se incluyen técnicas de diseño basadas en fórmulas matemáticas y lógicas en los siguientes apartados:

- Validación de las reglas de negocio.
- Integridad de los datos espaciales.
- Ciclo de vida del sistema.

## 4.1 Partición de Equivalencia

El diseño de los casos de prueba se fundamenta en técnicas sistemáticas de caja negra recomendadas por el estándar IEEE 29119, con el propósito de maximizar la cobertura funcional del sistema sin requerir la evaluación exhaustiva de todas las combinaciones posibles de datos de entrada.

Estas técnicas permiten construir casos de prueba repetibles, trazables y orientados a verificar tanto las reglas de negocio como las restricciones funcionales del Sistema Web de Gestión de Incidencias Georreferenciadas.

Para este proyecto se emplean las siguientes técnicas de diseño:

- Partición de Equivalencia.
- Análisis de Valores Límite.
- Transición de Estados.

## 4.1 Partición de Equivalencia

La técnica de Partición de Equivalencia consiste en dividir el dominio de entrada en grupos de datos que se espera produzcan un comportamiento equivalente del sistema. En lugar de evaluar todos los posibles valores, se selecciona un representante de cada partición válida e inválida, reduciendo el número de casos de prueba sin afectar la cobertura funcional.

En el presente proyecto esta técnica se aplicará principalmente en la validación de formularios de registro de incidencias, clasificación por tipo y subtipo, selección de prioridades, asignación de responsables y validaciones realizadas por el frontend y el backend. Asimismo, permitirá verificar que únicamente se acepten valores pertenecientes a los catálogos definidos por la base de datos y que los datos inválidos sean rechazados adecuadamente.

## 4.2 Análisis de Valores Límite

El Análisis de Valores Límite se utilizará para verificar el comportamiento del sistema ante valores ubicados en los extremos de los rangos permitidos, ya que estadísticamente es en estos puntos donde suelen concentrarse la mayor cantidad de defectos.

Esta técnica será aplicada sobre restricciones tales como:

- Coordenadas geográficas (latitud y longitud).
- Longitud máxima de nombres y comentarios.
- Límites establecidos para identificadores y catálogos.
- Restricciones numéricas definidas por el sistema.

Para cada rango se considerarán valores inmediatamente inferiores, iguales y superiores a los límites establecidos, verificando que el sistema acepte únicamente los datos válidos y rechace aquellos que incumplan las restricciones.

## 4.3 Transición de Estados

La técnica de Transición de Estados permite diseñar casos de prueba basados en los diferentes estados que puede adoptar una entidad durante su ciclo de vida, así como las transiciones válidas e inválidas entre ellos.

En este proyecto será utilizada para verificar el flujo de gestión de incidencias, comprobando que únicamente se permitan cambios de estado autorizados y que cada transición registre correctamente la información de auditoría correspondiente, incluyendo el usuario responsable, la fecha del cambio y el comentario justificativo cuando sea requerido.

Asimismo, se validará que el historial de estados conserve la trazabilidad completa de cada incidencia durante todo su ciclo de vida.
